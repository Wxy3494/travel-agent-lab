**新增发现，按优先级排列**

1. **P1：明确要求“预算不变”，模型错误仍可能改掉预算。**

用户输入“预算不变，第二天轻松一点”。在可控的意图模型替身中注入 `changes.budget=9000`，原预算6000；通过真实TourAssistant.handle和业务服务后，新版本实际保存9000且changed=true。app/assistant.py:72的safe_patch对关键字段只检查是否出现相关关键词，出现“预算”就允许修改，没有识别“不变”的约束。

这是保护层的故障注入证据，不能声称线上模型已经产生过这次误读。修复应优先识别明确的保留/否定要求，给受保护字段建立字段级修改授权；预算等数字必须与用户明确给出的新值对应。用户只要求调整第二天时，不得改变其他条件。验收应覆盖“预算不变”“别改人数”“不是改成9000”等否定表达，并注入与之矛盾的模型补丁，确保不落库。

2. **P2：中断后的聊天请求无法按原标记恢复。**

begin_chat先写入response=NULL的请求记录。模拟意图处理中取消任务，再重新实例化Repository和TravelService，用同一request_id重试，仍返回“这条消息正在处理中”。app/storage.py:95没有处理中租约、过期状态或恢复逻辑；app/assistant.py的完成写入仅在正常处理末尾执行。数据重开后旧锁定记录仍存在，因此进程退出也不能清理这类状态。

修复应给聊天任务增加pending/running/completed/failed等状态和租约，记录关联的行程版本，并在重试时辨认是否已经完成业务写入；对尚未完成的任务允许安全恢复。仅捕获CancelledError不足以处理进程崩溃，直接删除幂等记录则可能重复执行已提交的修改。验收覆盖意图中断、规划中断、行程提交后回复保存前中断，以及重启后原request_id重试。

3. **P2：独立审计未检查活动与预算账目是否完整对应。**

对正常ready行程的副本保留全部活动，删除10条交通/门票费用，仅保留住宿餐饮并重新求和，预算从496～1544元变成460～760元；audit_result仍返回空错误列表。app/audit.py:161检查现存条目的算术和住宿/餐饮数量，未普遍验证每个收费活动是否存在对应预算条目。新入场核验对部分受强制核验的门票有额外校验，但不能覆盖一般交通及演示/旧版门票。

该结果证明独立审计的完整性缺口，不代表正常生成流程已观察到漏账。修复应建立事件与预算条目的稳定关联，核对每笔应计费用的存在、数量、金额、来源，检测重复和孤立条目；明确餐饮/住宿汇总计费的例外。验收用删除、重复、错绑事件、只改总额等变异样本，全部必须报错。

4. **P3：交通总时长被改成0后，审计不会发现。**

原行程两天交通总时长分别125、121分钟，保留交通事件但把两个travel_minutes都设为0，审计仍无错误。原因是app/audit.py:134的条件额外要求day.travel_minutes为真，零值被跳过。应统一重新汇总检查；如果零值用于兼容旧数据，应以明确的数据版本或缺失值区分。验收要求“存在交通但汇总为0”的结果被拒绝，同时无交通的真实零值通过。
