**已经完成的能力**

- 用户流程：六项基础输入、一次集中追问、表单生成、自然语言修改、地点歧义确认与明确冲突选择。
- 行程组织：单城/跨城、城市顺序、必去/排除、人数/房间、时间窗口、餐饮休息、酒店/车站坐标接驳、每日路线耗时及雨天候选。
- 计算与纠错：Python 物化日程、全团预算、来源记录、独立审计和最多两次返工；模型审核无法豁免代码硬错误。
- 状态和数据：SQLite 版本快照、旧版读取、差异比较、从旧版复制、base_version 冲突检测及 Markdown 导出。
- 工程基础：Provider 与 Agent 可替换、离线演示、官方 SDK 回放、模拟 HTTP 测试、一键启动、来源类型及调用/token 指标。

三角色并非只写在 README 中：AutoGenAgents.research 实际创建 researcher 并调用 collect_city，planner 返回结构化 Selection，reviewer 返回 Review，TravelService 控制返工。它属于固定流程编排的多 Agent 系统。固定流程适合当前任务，但“增加角色”本身不能作为质量更高或效率更好的证据。DemoAgents 是规则实现，离线成绩不能归因于模型协作。

**优先修复的问题**

1. **P1：源码发布包遗漏 UI 必需文件。** scripts/package_public.py:13 的后缀白名单没有 .css/.jpg；现有 ZIP 也确认缺少 app/ui_theme.css 和 app/assets/coastal-evening.jpg，而 app/ui.py:27、29 在启动阶段直接读取它们。交付该包会让页面启动缺少依赖文件。应明确纳入静态资源，并在临时目录解压后执行 UI 启动冒烟检查。验收标准：脱离当前源码目录，ZIP 可以启动页面并显示样式、图片。

2. **P2：非法日序被接受。** app/schemas.py:109 的 day_place_ids 使用普通 int 键，consistent 只检查上界。实测 0、-1 可以通过 Schema 且最终 ready，指定活动没有按合法日序应用；-100 最终变为 internal_error。应对键使用正整数约束并核验 1≤day≤days。验收标准：0、负数及超出旅行天数的日序统一在 API 输入边界返回 422。

3. **P2：跨城平均分配造成错误的容量判断。** app/planning.py:49 按城市平均分天，app/service.py 在模型选择前据此计算必去景点容量。实测广州→深圳共 5 天、深圳 7 个必去点，被按广州 3 天/深圳 2 天判定最多 6 处而拒绝；使用相同人工样例，广州 2 天/深圳 3 天的候选安排通过物化检查和独立审计。应联合计算各城最低需求、接驳耗时和天数分配，再判断不可满足；不能将初始平均分配当成固定容量。验收标准：该用例可重新分配天数，确实不可满足的用例仍给出清楚原因。

4. **P2：前后端超时契约不一致。** app/ui.py:128 的 HTTP 等待为 200 秒，后端默认超时为 300 秒。耗时较长时前端可能先显示连接失败，而后端仍在执行或已保存；重复点击还可能造成额外请求。此处依据代码确认，未进行 200 秒实等实验。短期统一超时配置并处理重复提交；长期用任务 ID、阶段状态查询、取消和幂等键。验收标准：模拟慢任务下，页面能区分排队、执行、失败和完成，刷新后能找回结果。

5. **P2：30 天上限迁移不完整。** app/adjustments.py:17、45 仍用 c.days < 7 决定是否允许“增加一天”。实测 7 天时间冲突只给缩短游览建议，不会提供第 8 天选项，即使 Schema 支持 30 天。应复用 MAX_TRIP_DAYS 并测试 7、29、30 天边界。

6. **P2：验收文档和交付状态不同步。** README 首段、COMPLETION、EVALUATION、RESUME_EVIDENCE 等仍有 104 项测试和“真实接口未验收”的旧表述；LIVE_ACCEPTANCE 记录了广州真实小样本，10-16 记录为 129 项测试。应生成一份带日期、源码哈希、验证范围的验收摘要，各文档引用它。当前目录也没有 .git；若要作为正式作品交付，需要建立版本历史、选择许可证，并保留真实 CI 记录。

酒店搜索链接、默认单价及四天天气接口不等于实时房价、房态或长期预报。七天天气已有适配约定和模拟测试，真正缺少的是接入与验收；不能算作完全没有天气功能。出行日尚未进入预报期时，应支持临近出行刷新，不应填入预测之外的确定天气。

**工程和算法改进**

- 将研究、名称确认、天数分配、物化与审计、持久化拆成可单独观测的阶段。TravelService.execute 的职责较多，但当前体量无需为了形式拆成微服务。
- 为同一地图账户提供跨请求限流和有界共享缓存。现有锁与缓存属于每次新建的 AmapProvider，多请求之间不会共享节流；历史单请求通过不能证明并发稳定。
- 增加任务级和日级费用上限、输入规模限制及失败请求用量统计。现有模型调用次数上限和 token 指标有价值，但不等于全局金额熔断或真实账单。
- 保留 SQLite 用于本地单人场景，增加备份、恢复、数据版本迁移和索引；如果转向公开服务，再引入身份、资源归属、配额与删除策略。
- 改进长行程资料获取：目前只读搜索第一页、兴趣查询最多取前两项；可按天数和偏好补充候选并分页检索，避免扩大到 30 天后大段自由活动。路线排序仍是有限候选比较，不能宣称全局最优。
- 来源记录继续保留脱敏原则，同时补充更细的查询摘要、适用日期、数据哈希和官方页面依据，让“有来源”进一步变成“可复核”。

**下一轮评测应补什么**

1. 将本轮复现缺陷加入独立回归用例；发布包必须在解压后的干净目录验收，不能只在原目录跑测试。
2. 跑已准备的四条真实规划及一次修改；另选未用于调试的城市、未来日期、同名分店和复杂时间窗，记录成功与失败，不扩大城市覆盖结论。
3. 做同模型、同数据、同约束的 single/multi 配对评测。至少多次重复，报告约束通过率、错误拒绝、修复成功率、用户偏好满足、端到端 P50/P95、模型及地图调用、token 和费用。当前单 Agent 基线由代码查询资料、多 Agent 增加研究和审核，结论应限于这套分工的增量。
4. 引入独立人工评分和用户试用，关注“是否真想按它出行”“需要手工改多少”“是否看懂估算和风险”。既有 40 条是已知契约回归，不能充当盲测质量成绩。
5. 进行多请求限流、取消、超时、持久化恢复和新机器安装测试；有 Docker 后验证构建、health、UI 和重启持久化。

建议实施顺序：**先修复交付和输入边界 → 修复跨城分天 → 完成真实跨城验收与对照 → 补开放/票务数据 → 改进任务进度、地图与导出 → 按公开服务需求补账号和部署。**
