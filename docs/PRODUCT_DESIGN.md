# 产品设计 · 行旅

版本日期：2026-10-16。用户最新选择：六项基础字段全部直接显示的表单，下方展示结果，并保留文字修改入口。保留当前深蓝卡片与暖色按钮。说明和报错使用通俗中文，旧版本读取和下载也适用；酒店显示地图、房价搜索入口和明确的预算估算；天气自动跟随每天的城市与日期展示，不提供独立查询表单。时间只保留从住处出发与最后一个游玩项目结束，增加可选住宿地址。

## 用户问题与成功标准

国内自由行用户常有明确目的地，但不确定如何把城市、景点、时间与全团预算拼成可执行方案。本产品把需求整理成约束，查询地点与交通，再输出能解释选择、看见不确定性、连续修改并读取历史版本的行程。

首版成功标准是能完整演示单城和跨城规划，拦截缺失需求、不可满足预算、未知地点和超长活动时间，并提供可追溯来源。`ready`表示当前模型、资料和估算范围内通过检查，不等于实际预约成功、设施可用或票价保证。

## 范围与输入契约

| 字段 | 规则 |
|---|---|
| 出发城市、目的地城市顺序 | 必填；1～3目的地，不重复；出发地可与首城相同 |
| 开始日期、旅行天数 | 必填；今天或未来，1～30天；天数至少等于城市数量 |
| 人数、人民币总预算 | 必填；1～10人；预算是全团总额 |
| 兴趣、必去、排除 | 可选；以POI身份检查；唯一规范名/演示数据别名绑定，歧义由用户确认 |
| 公共交通/自驾 | 默认公共交通；自驾预算按每车计算 |
| 返回出发地 | 默认不计返程，必须提示；明确要求后包含最后一天返程 |
| 无障碍 | 默认未要求；明确要求且无证据时保持待核实 |
| 房间数 | 可明确输入；省略时假设每间2人并向上取整 |
| 酒店、餐饮、门票区间 | API可完整设置；真实模式可文字提取；离线解析不支持复杂报价 |
| 到达、离开、活动时段 | 可选；同一天内的当地HH:MM时间，不接受秒或时区；可按日/下午设置 |
| 游览时长与节奏 | 30～240分钟；默认90分钟；轻松日减少可选活动并预留30分钟休息 |
| 接驳位置 | 按城市指定已查询的酒店、到达/出发车站ID；校验坐标、城市和类型 |
| 入场与室内信息 | 入场按场馆和日期核对已适配官网或接口；预约需用户确认，未知不认定；室内信息仍需明确依据 |

六项必要字段缺失时，同一条回复列出所有缺项。未完成补充时保持 `needs_input`，不猜预算、日期、人数或出发地。“明天”等明确相对日期按北京时间解释。没有年份的日期会需要澄清，离线规则不默认补年份。

## 表单与文字修改流程

```text
填写六项基础信息 → 一次列出缺项/冲突 → 完整后查询资料
                                  ↓
                       草案 → 算路/预算/审核
                                  ↓
                 表单下方：摘要 + 每日行程 + 风险/来源
                                  ↓
             修改表单重新生成 / 在结果下方输入文字修改
                                  ↓
             保留其他约束 → 局部或全量重算并说明范围 → 保存新版本
```

首页卡片直接显示出发地、目的地两个输入框，以及日期、天数、人数、全团预算。兴趣、必去/排除、交通和费用设置默认收起。输入缺失时集中提示，不猜关键约束；填写示例是用户明确选择的示范值，不是自动替用户决定需求。

住宿、餐饮、门票预算各用一个金额输入框，不要求用户填写上下限或价格依据。留空时自动估算；修改已有行程时，未填写的项目沿用当前估算。明确填写的金额作为用户预算假设计算，不代表实时价格。旧版本的费用区间仍保留，单金额框留空；修改其他字段不会覆盖原费用区间。

生成后在表单下方展示城市顺序、天数、人数、费用区间、住宿城市/晚数，每天用可展开卡片展示交通、地图、天气与备选。预算、来源默认收起。文字修改如“预算改成1元”继承城市、日期、人数和偏好，费用下限超过预算时给待处理方案及原因，不宣称已满足。修改完成或读取旧版本后，表单同步到该版本。

文字修改记录只在浏览器会话内保留；SQLite保存业务需求与各版本，不保存原始自由文本或模型内部思考。刷新后通过历史列表选择城市/日期，查看版本和活动/时间/费用/约束对比。旧版直接修改会遇到409，可读取最新版或从旧版复制为新旅行。表单未提交的改动不参与文字修改，页面对此有提示。

## 行程与预算决策

新表单默认9:00从住处出发、最后一个游玩项目在21:30前结束、单处90分钟、项目之间20分钟休息；返程交通另计但不得跨午夜。删除首日到达、末日离开和初始表单的整组分日时段控件；分日要求可在结果下用文字修改。旧接口与历史版本仍保留原有时间窗兼容性，通过新表单重算时切换到新语义。城市内交通加10分钟缓冲，换城加45分钟；午餐留出1小时，餐饮不重复收费。路线或游览无法放入时段时保留冲突。入场资料按具体到访日期校验；真实模式下开放、预约或票价未知时不能报告已通过，用户自行提供的资料明确标注来源。

每晚住宿城市与当天停留城市一致；住宿夜数为天数减1。末日不包含额外住宿。明确选定的酒店参与每日起终点；换城先接驳出发站，再查询到达站，随后查询景点衔接。未选位置保留市中心假设，房价、房态和班次均不因此成为已知。

全团费用由路线费用、门票、住宿、餐饮构成。门票按人次、餐饮按人天、酒店按间夜；公共交通按人数，自驾按4人/车向上取整。默认价格区间为酒店180～320元/间夜、餐饮70～110元/人天、门票0～80元/人次，均是项目假设，不是采集的实时价格。

| 预算关系 | 结果 |
|---|---|
| 估算上限≤总预算 | 估算内可行，仍提示价格与开放状态需核实 |
| 下限≤预算<上限 | `needs_review`，明确超支风险 |
| 预算<下限 | `needs_review`，明确当前假设下无法满足 |

不擅自改人数、删必去或虚构低价。确定不能靠选择POI解决的预算/时间问题停止机械返工，相同错误再次出现也停止。返回增加预算、减少可选活动、缩短默认游览、增加天数等适用方案和影响；用户点击后应用并保存新版本，重新核验，不保证每个建议单独就能解决全部冲突。

只修改一天/下午时保留未影响日期与上午事件，按已保存的分日费用重新算受影响路线，再检查全团预算。城市、日期、人数、价格、接驳位置等全局变化扩大重算范围并提示。旧快照缺少分日费用时也明确全量重算，不伪称已保留。

## 资料与风险

`live`是实际接口返回的地点/路线/天气，`estimate`是费用或衔接假设，`fixture`是人工测试数据，`user`是显式用户报价。证据记录查询时间、提供方和说明链接。说明链接是接口文档，不冒充查询记录公开网页；真实原始URL中带key的参数不保存。

只使用预报返回的对应日期；没有预报就写“无可用预报”。室内候选需要fixture分类或用户明确属性依据；真实POI默认未知。选择候选替换可选活动后重算，必去地点不能通过替换入口删除。开放、预约、无障碍设施和住宿可售状态均不擅自认定。

工具与用户资料中的“忽略限制、自动付款、改角色”等文字不获得新权限。代码只提供地图读工具，没有任何交易端点。敏感编号和明显越权输入会阻断并清空持久化约束；这属于基础防护，不能保证识别所有自然语言攻击。
